模型 `gpt-6-astra`，错误 `stream_read_failed`，耗时 7204 ms。

已收到 edit 工具的参数增量，随后收到错误并停止；网关未收到终态用量。
供应商采用默认 300 秒超时，这次 7.2 秒的失败不支持调大超时的结论。

旧代码隐藏了底层读取错误，无法追溯本次究竟是连接重置、unexpected EOF
还是其他读错误。已交付工具参数导致网关无法安全重放请求，这是此次可修复的
恢复缺口。会话在用户继续后还有正常完成的请求，服务并未持续不可用。

## 当前方案：实时转发，限定重试范围

- 撤掉工具事件缓冲，函数工具开始和参数增量立即交付；文本和推理保持实时转发。
- 读错误或缺少终态的 EOF，只在尚未交付任何事件且未取消时，等待 250 ms 后
  最多重试一次。工具开始事件一旦交付，也禁止重试。
- 下游 emit 失败、客户端取消、上游业务错误不触发此重试。
- `response.completed` / `response.incomplete` 处理完立即结束，不再等待
  HTTP 关闭；避免完成后的断链被误报为模型失败。
- 读取错误携带底层原因、HTTP 协议、上游 x-request-id 和最后一个事件类型，
  经错误响应返回 DSH，供后续定位；不记录请求内容和认证信息。

当前方案避免额外工具缓冲的内存及等待开销，仅恢复尚未交付输出的断流。
截图中已经交付工具参数的故障仍不能在网关内自动恢复：客户端需要配合丢弃
未执行调用并重试，或上游提供可靠的恢复机制。具体底层原因尚未确定，
不应把这次调整当作网络故障已经根治。

无输出阶段的重试仍可能产生第二次上游推理请求；未返回 usage 的失败尝试
仍按现有 unavailable 口径记录。
