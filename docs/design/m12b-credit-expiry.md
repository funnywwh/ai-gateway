# M12b 设计记录：赠送额度到期冲销

> ⚠️ 流程说明：本文是**先实现、后补写**的设计记录（本轮唯一一次），因为它是 M12 的收尾小项、
> 与既有 `docs/billing.md` §5 的约定一致。流程要求在编码前输出设计文档，这次没有做到，
> 记录在此以便自查；正文描述的是已落地的语义。

## 1. 问题

规格：`docs/billing.md` §5「赠送额度带 `expires_at`，到期由每日作业按 `expire` 冲销**未使用部分**
（不动充值余额）」。难点不在代码量，而在**额度归属**：账本是单一余额流水，没有「这笔消费花的是哪批额度」的记录。

## 2. 归属模型（明确写死的策略）

采用**按到期时间先进先出**的消费归属：

1. 取所有「已到期、且尚未冲销」的 `credit_grant` 账本行，按 `expires_at` 升序；
2. 逐笔冲销 `min(该笔赠送额, 账户当时可用余额)`，冲销后余额递减，**永不为负**；
3. 每笔写一条 `kind=expire`、`amount=−冲销额` 的账本行，`ref_id` 指向赠送行的 `idem_key`；
4. 余额不足时该笔冲销 0（仍写一条 0 额 `expire` 行）：**记录决定，保持幂等**。

含义：**付费充值的额度最后才被消费**（对客户最有利的读法）。这是策略选择，不是可观测事实，因此在代码注释、
接口返回与本文里都写明。要改成「按入账顺序」只需改排序键，不需要改表结构。

## 3. 幂等与并发

- 幂等键 `expire:<赠送行 idem_key>`，`ledger_entries.idem_key` 唯一 → 重复运行、重启后重跑、多进程同时跑都不会重复冲销；
- 「是否已冲销」用 `NOT EXISTS (SELECT 1 FROM ledger_entries WHERE kind='expire' AND ref_id = 赠送行 idem_key)` 判断，
  不额外维护状态字段；
- 事务边界：每账户一次 `AppendLedger`（一个事务里写该账户当次全部冲销行），余额在同一事务内更新。

## 4. 调度与入口

- 启动时跑一次，之后每 24 小时一次（`Service.StartExpiryJob`）；到期是**日级策略**，不需要实时；
- 管理面 `POST /admin/api/v1/billing/expire-credit` 可手动触发并返回结果（`scanned/expired/skipped/expired_micros`），
  便于运维当场核对而不必等调度；
- 单次扫描上限 500 笔，超出部分留到下一轮（避免一次作业长时间持有写锁）。

## 5. 数据模型

迁移 `0003_ledger_expiry.sql`：`ALTER TABLE ledger_entries ADD COLUMN expires_at INTEGER`。
选择加列而不是建 `credit_lots` 表，理由是：批次的**剩余额**其实是「余额 + 冲销记录」的派生量，
单独存余量会引入第二份真源与不一致风险；NULL 表示「不过期」，历史行天然兼容。

## 6. 不变量的保障

- 冲销额被可用余额夹住 → 不变量 4（预付余额不为负）不会被破坏；
- 冲销是普通账本行 → 不变量 1、2（余额 = Σ 账本、末行 balance_after = 余额）自动成立；
- 冲销不产生 usage → 不变量 3（Σcharge = Σusage.charge）不受影响。
实测：冲销前后 `billing/invariants` 均为 `ok=true`。

## 7. 测试

1. `TestGiftCreditExpiresOnlyTheUnusedPart`：到期的 0.40 被冲销、未来的 0.90 与充值 1.00 保留；二次运行 `expired=0`；
2. `TestGiftCreditNeverTakesTheBalanceNegative`：两笔到期赠送共 1.00、已消费 0.70 → 只冲销 0.30，余额归零不为负，不变量成立；
3. 端到端实测：充值 1.00 + 到期赠送 0.50 + 未来赠送 0.25 → 冲销后余额 1.25，账本出现 `expire -500000`，二次触发 `scanned=0`。

## 8. 未做/边界

- 不追溯「历史到期但当时余额不足」的补冲销：那笔已经以 0 额记录，语义是「到期时没有可用余额可冲」；
- 没有对外通知（如邮件/告警）：到期金额可从 `expire` 账本行或 `get_ledger` 工具读取；
- 逾期很久的赠送不会累积惩罚，只是保持在账本里可查。
